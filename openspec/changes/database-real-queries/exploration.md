### Data Mapping Verification

#### 1. `GET /api/metrics/sales` → SalesData[]
**Query**: Top 5 states by `SUM(price + freight_value)` on weekends.
```sql
SELECT c.customer_state AS category,
       ROUND(SUM(o.price + o.freight_value)::numeric, 2) AS amount
FROM "proyecto1-Data-Engineering".fact_orders o
JOIN "proyecto1-Data-Engineering".dim_customers c ON o.customer_key = c.customer_key
JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
WHERE t.is_weekend = true
GROUP BY c.customer_state
ORDER BY amount DESC
LIMIT 5
```
- **Percentage**: Computed in JS: `(amount / totalAmount) * 100`, then `roundPercentages()`.
- **Status**: ✅ Feasible. Types align perfectly.

#### 2. `GET /api/metrics/users` → UserData[]
**Query**: Monthly distinct customers that ordered on weekends (cumulative).
```sql
WITH monthly AS (
  SELECT t.year, t.month,
         COUNT(DISTINCT o.customer_key) AS new_users
  FROM "proyecto1-Data-Engineering".fact_orders o
  JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
  WHERE t.is_weekend = true
  GROUP BY t.year, t.month
  ORDER BY t.year, t.month
)
SELECT TO_CHAR(MAKE_DATE(year, month, 1), 'YYYY-MM') AS month,
       new_users AS "newUsers",
       SUM(new_users) OVER (ORDER BY year, month) AS "totalUsers"
FROM monthly
```
- **Status**: ✅ Feasible. `totalUsers` uses a window function for cumulative. Month formatted as `YYYY-MM` to match existing `UserData.month`.
- **Risk**: Depends on `MAKE_DATE` availability (PostgreSQL 9.4+). If not available, concatenate `year || '-' || LPAD(month::text, 2, '0')`.

#### 3. `GET /api/metrics/visits` → VisitData[]
**Query**: Daily order count on weekends.
```sql
SELECT t.full_date::text AS date,
       COUNT(o.*) AS visits
FROM "proyecto1-Data-Engineering".fact_orders o
JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
WHERE t.is_weekend = true
GROUP BY t.full_date
ORDER BY t.full_date
```
- **Status**: ✅ Feasible. Types align.
- **⚠️ Gap**: Returns ONLY weekend days (not 30 consecutive days like mock). The existing LineChart handles sparse data fine, but the visual will show gaps. Consider whether to pad or to relabel the chart.

#### 4. `GET /api/metrics` → MetricsSummary
**4 DB queries**:
```sql
-- totalUsers
SELECT COUNT(DISTINCT customer_key) AS value FROM "proyecto1-Data-Engineering".fact_orders

-- activeUsers
SELECT COUNT(DISTINCT o.customer_key) AS value
FROM "proyecto1-Data-Engineering".fact_orders o
JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
WHERE t.is_weekend = true

-- totalSales
SELECT ROUND(SUM(price + freight_value)::numeric, 2) AS value
FROM "proyecto1-Data-Engineering".fact_orders o
JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
WHERE t.is_weekend = true

-- totalVisits
SELECT COUNT(*) AS value
FROM "proyecto1-Data-Engineering".fact_orders o
JOIN "proyecto1-Data-Engineering".dim_time t ON o.time_key = t.time_key
WHERE t.is_weekend = true
```
- **conversionRate**: `Math.round((activeUsers / totalUsers) * 100)` — computed in JS.
- **Status**: ✅ Feasible.
- **⚠️ Semantic shift**: `totalUsers` now means "distinct customers who ever ordered" (not "total registered users"). `conversionRate` is now "weekend-customers / all-customers", which is inherently a different KPI from the mock's "active / registered".

### Risks

1. **Schema quoting**: The schema `"proyecto1-Data-Engineering"` (with hyphens) MUST be double-quoted in SQL. Easy to forget. All 4 query functions need consistent quoting.

2. **Month format mismatch**: `dim_time` has `month_name` (text, e.g. "January") and `month` (numeric 1-12). If the model uses `month_name`, the `UserData.month` field ("2024-01" expected by `UserChart.xAxis`) will break. **Must use `year + month` → `YYYY-MM` format.**

3. **Test strategy — how to mock DB**: Current tests mock the mockData module. For models, we must either:
   - Mock the `pg.Pool` query method (`pool.query`), OR
   - Extract a query interface and mock that.
   - Preferred approach: export a `query` wrapper from `models.ts` that can be mocked in vitest.

4. **Visits chart sparseness**: Mock returns 30 dense days. Real DB returns ~8-13 weekend days per month. The line chart will have visible gaps. Relabeling to "Órdenes en Fines de Semana" and accepting gaps is simplest. Or pad with zero-visit days for a smoother line.

5. **Empty tables**: Need to handle `totalUsers === 0` to avoid division by zero in `conversionRate` calculation.

6. **No migration tooling**: raw SQL only. Schema changes (if needed) must be manual.

7. **`pg` Pool vs Client**: The existing `db.ts` uses `Pool` (connection pooling), which is correct for API routes. No change needed.

### Recommendation

**Proceed with proposal and implementation.** The data mapping is solid. The main architectural decision is **how to structure `models.ts`**:

- **Option A**: Export 4 standalone functions, each creating their own `pool.query()` call. Simple, but hard to test (need to mock `db.ts`).
- **Option B**: Export a service object that receives a pool/client. Testable via dependency injection. More effort but cleaner.

**Recommendation**: Option B — inject the pool. Creates a clean seam for testing without mocking pg internals.
